私密聊天 · 系统框图集

v0.2 需求冻结稿 · 2026-11-16 · 基线 ChatRoom v5.4.0 · 仓库 klmycjs/private-chatroom · 配套 docs/17 需求分析报告、docs/18 设计方案

图 1　总体系统架构

发起人走 HTTPS 门户申请、自动通过后由签发器生成房间身份密钥对并下载专属客户端；服务端分控制面与数据面，只登记公钥、只转发密文，不接触任何可解密聊天内容的材料；朋友用单文件 HTML 只与数据面建立密文通道。HTML 文件由发起人线下自行分发，服务端不参与。

控制面 / 数据面 / 客户端线下分发路径（不可控）

图 2　房间生命周期状态流转

申请提交即自动通过、无人工审批队列；TTL 默认 24 小时、上限 72 小时，从签发时刻起算；定时器与每次请求惰性检查双保险，进程重启后扫描补清理，销毁后不可恢复。

图 3　双层加密与密钥分层（Q-02 已冻结）

L1 是 TLS 传输加密，只保护链路、由服务端终止；L2 是应用层端到端加密，内容密钥按每个成员的公钥分别封装。服务端全程只有公钥与密文，不持有任何可解密聊天内容的私钥或对称密钥；房间公钥 RK_pub 只用于验签，不用于加密内容（否则朋友端无私钥可解）。

L1 传输加密（服务端终止）L2 应用层密钥与加密服务端可见边界

图 4　单条消息的加密封装与转发时序

发送方本地随机生成内容密钥、加密消息、按当前已验签的全部成员公钥逐一封装，并用自己的成员私钥签名；服务端只校验结构、成员集合一致性与签名后落库转发；每个接收方用自己的私钥解出内容密钥、解密并验签。

Q-02 已冻结 · 双层加密房间身份密钥对内置公钥 + 每成员本地密钥对；内容密钥逐成员封装，服务端零解密能力，可准确宣称端到端加密。
