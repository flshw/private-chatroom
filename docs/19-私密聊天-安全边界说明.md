# 私密聊天 · 安全边界说明

> 版本：v0.1  
> 日期：2026-11-16  
> 对应代码：`PC_RELEASE_VERSION = 0.1.0`，`PROTOCOL_VERSION = 1`  
> 权威设计：`docs/18-私密聊天-设计方案.md`

本文回答一个问题：**这套系统到底能保证什么，不能保证什么。** 所有措辞以可验证的代码行为为准，不沿用主线 ChatRoom 的 KDC 表述。

---

## 1 安全结论

当前实现可以保证：

1. 服务端不持有任何聊天内容密钥，无法解密文字、文件与语音内容。
2. 每条消息使用独立的 `K_msg`，并按每个成员公钥单独封装；不存在可被服务端或单一成员复用的“房间共享密钥”。
3. 客户端内置配置块由平台签名密钥 `SSK` 签名，房间级成员公钥清单由 `RK` 签名，且每条成员公钥带成员自签名。
4. 服务端校验消息签名、序号、时间偏差与 wraps 完整性；重放、漏封装、篡改密文会被拒绝。
5. 房间到期、吊销、销毁或重新签发时，服务端会删除对应 `RK` 私钥并踢出旧连接；数据库与文件中的密文随房间销毁级联删除。

当前实现**不能**保证：

1. 专属 HTML 文件不被转发。文件本身就是准入凭证，拿到文件的人在有效期内可以入房。
2. 成员设备没有恶意软件、浏览器扩展或被篡改的客户端代码。
3. 服务端不拒绝服务、不丢消息、不记录元数据。恶意服务端可以破坏可用性，但不能从协议中获得内容明文。
4. WebRTC 使用的外部 STUN 服务不看到参与者 IP 等网络元数据；这部分不由本系统控制。
5. 聊天内容的“永久前向保密”。本版提供按消息临时密钥与按成员封装，但没有实现双棘轮等长期会话前向保密机制。

---

## 2 密钥与凭证边界

| 名称 | 生成位置 | 存放位置 | 用途 | 是否上传 |
|---|---|---|---|---|
| `SSK_priv/pub` | 服务端 `KeyStore.init()` | `PC_KEYS_DIR/ssk-private.pem`、`ssk-public.pem` | 签发客户端配置块 | 公钥进 HTML，私钥不上传 |
| `serverSecret` | 服务端 `KeyStore.init()` | `PC_KEYS_DIR/server-secret` | `joinToken` 的 HMAC 摘要 | 否 |
| `RK_priv/pub` | 每次签发/重新签发 | 私钥在 `PC_KEYS_DIR/room-<id>-*.pem`，公钥进配置 | 签发成员公钥清单 | 公钥进 HTML，私钥不上传 |
| `joinToken` | 服务端签发器 | 明文只在 HTML 中；数据库只存 HMAC | 入房认证 | 不单独上传 |
| `UK_priv/pub` | 成员浏览器本地 | 仅浏览器内存 / 本地复用位置 | 解封装、签名 | 只上传公钥 |
| `K_msg` | 每条消息发送方本地 | 仅浏览器内存 | AES-256-GCM 加密正文 | 不上传；只上传按成员封装后的 wrap |
| `K_file` | 文件发送方本地 | 仅浏览器内存 | 加密文件或语音 | 不上传明文；作为普通 E2EE 消息正文发送 |

结论：服务端数据库中只有公钥、签名、HMAC 摘要、密文、`iv/tag` 与元数据。没有任何字段可以单独还原聊天内容。

---

## 3 三重公钥防替换

客户端不会盲目相信服务端广播的公钥。

1. **配置块验签**  
   HTML 中的 `window.__PC_CONFIG__` 与 `window.__PC_CONFIG_SIG__` 由 `SSK_priv` 签名，内置 `SSK_pub` 验签。任何字段被改动都会导致拒绝启动。

2. **成员清单验签**  
   服务端广播的 `memberList` 由当前 `RK_priv` 签名，内置 `RK_pub` 验签。重新签发会轮换 RK，旧清单无法再用。

3. **成员自签名**  
   每个成员条目都带 `selfSig`，使用该成员自己的 `ukPub` 验证。服务端不能把第三人公钥替换进清单而不被客户端发现。

4. **版本单调**  
   `memberList.version` 必须严格递增，旧清单重放会被客户端和服务端拒绝。

相关测试：`tools/verify-pc-crypto.js` 已覆盖配置签名、公钥替换拒绝、旧清单拒绝、RK 轮换与旧 RK 销毁。

## 4 消息完整性与服务端可见范围

消息签名只覆盖 `signedPart()` 定义的固定字段：

```text
v, roomId, senderSid, seq, ts, kind, iv, ct, tag, wraps
```

`meta` 等展示字段不参与签名，避免历史回放时因展示层变化导致验签失败。

服务端在数据面执行：

- `joinToken` HMAC 比较；
- 房间状态与 TTL 检查；
- 成员人数上限；
- `selfSig` 验证；
- `seq` 严格递增；
- 时间偏差在 `CLOCK_TOLERANCE_MS` 内；
- `wraps` 必须覆盖当前全部成员；
- 消息 RSA-PSS 签名验证；
- RTC 信令只按目标成员公钥封装后转发。

服务端**可见**：房间 ID/名称/TTL/人数上限、成员昵称、公钥、连接 IP、消息时间、消息大小、密文与签名。  
服务端**不可见**：消息正文、文件明文、语音明文、`K_msg`、`K_file`、成员私钥。

门户公开目录 `GET /pc/api/rooms/public` 无需登录即可读取所有已签发、未到期、未吊销的房间，但**只返回白名单字段**（房间名、状态、剩余时间、人数上限、当前在线人数）。它不返回房间 ID、`joinToken`、任何密钥/签名、房主身份或成员信息；看到房间名并不等于获得准入资格，加入仍须房主分发专属客户端文件。房主可在门户「我的房间」中随时自行销毁房间，销毁后立即从公开目录移除、踢出全部在线成员并删除所有密文。生命期可选 1 / 8 / 12 / 24 / 48 / 72 小时，默认 24 小时，硬上限 72 小时。

## 5 生命周期安全

| 事件 | 行为 |
|---|---|
| 申请房间 | 自动通过，生成房间 ID、joinToken、RK 密钥对与签名配置块 |
| 重新签发 | 生成新的 joinToken 与 RK；删除旧 RK 私钥；数据库更新 HMAC/公钥/摘要；踢出全部旧连接 |
| 吊销 | 设置 `revoke_at`，删除 RK 私钥，踢出连接；客户端状态检查返回 invalid |
| 销毁 | 广播过期；删除消息、文件 blob、房间行与 RK 私钥；清理成员会话 |
| 到期 | 启动与定时清理器统一调用同一销毁路径 |
| 管理员强毁 | 需 `X-PC-ADMIN-Token`；无令牌或令牌错误一律 403 |

注意：重新签发会立即使旧 HTML 失效，因此房主应在确认旧文件不再使用后操作；这是设计上的主动安全行为，不是故障。

## 6 文件、语音与视频

- 文件与语音在浏览器本地用一次性 `K_file` 加密后上传；服务端只保存密文 blob 与 `iv/tag`。
- `K_file` 以普通 E2EE 消息正文发送给成员，因此同样按成员公钥封装。
- 文件下载接口要求有效的房间会话 `sid`；它不是公开对象存储。
- WebRTC 媒体流是 P2P DTLS-SRTP；应用服务端只转发按目标公钥封装后的 signaling，不解密 signaling。
- 外部 STUN 用于 NAT 穿透，会看到网络层元数据；这不改变应用层内容加密，但属于隐私边界的一部分。

## 6.1 双版本客户端与联机掼蛋（豪华版）

- 两个版本共用同一套 E2EE 通道与配置签名；豪华版只是额外内联掼蛋规则引擎、轻量 3D 场景与游戏 UI，仍为单文件、无外部资源，不降低加密强度。
- 掼蛋发牌由房主在本地洗牌，每名玩家的手牌用一次性 `K_deal` 加密后按其公钥单独封装，经现有密文消息通道分发；服务端与旁观者都无法看到未向其封装的手牌。
- 出牌、过牌、进贡、升级等游戏动作都作为 `kind='game'` 的 E2EE 消息发送，沿用消息签名与 wraps 完整性校验，服务端只转发密文、不判定牌局。
- 旁观席位由服务端按首个申请者的 `ukPub` 权威锁定（`GAME_SPECTATE`），整局不可更改、不可被顶替；掉线重连仍识别为同一人。旁观者只能收到向其封装的游戏状态，不能出牌。
- 规则正确性依赖客户端本地引擎；由于服务端不参与判定，豪华版假定玩家客户端未被篡改，这是与"服务端权威判定"方案相互权衡的结果。

## 7 部署边界

- `server/data/` 保存 SSK 私钥、serverSecret、RK 私钥、数据库与文件密文。目录权限建议 `0700`，不得纳入公开静态目录，不得提交 Git。
- `PC_ADMIN_TOKEN` 必须在生产设置；留空时运维销毁接口全部拒绝。
- `PC_TLS_CERT` / `PC_TLS_KEY` 用于进程直出 HTTPS；若由反代终止 TLS，则两者留空，但要确保 `/pc/api/*` 与 `/pc/ws` 被正确转发，且 WebSocket Upgrade 头保留。
- 客户端配置里的 `serverUrl` 默认写 `https://flshw.online`，所有 WSS 连接应始终走 HTTPS 反代，而不是明文本地端口。
- 配置签名保护的是配置字段，不保护客户端 JS 代码本身。若分发渠道被篡改，用户可能拿到恶意 HTML；请通过可信渠道分发，并核对来源。
- `joinToken` 不得放进 URL query。v0.1 的 `/Pchat/p/:roomId` 只显示使用提示；这是为了避免浏览器历史、Referer、反向代理日志泄露准入凭证。
