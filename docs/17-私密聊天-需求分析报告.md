### 1.1 BR-20 加密细化逐条拆解

| 子项 | 用户原话 | 落地为需求 | 设计上的必要补全 |
|---|---|---|---|
| BR-20a | 聊天室建立时生成密钥对 | 房间建立时生成 **RK 房间身份密钥对**（RSA-2048/3072），服务端持有签名私钥 `RK_priv` | 【推断】**明确 `RK_pub` 的用途为「验签」而非「加密聊天内容」**：若只用公钥加密内容，只有持私钥者能解，而朋友只有公钥，数学上无法解密。因此 RK 用于签名房间公告与成员公钥清单，不参与内容加密 |
| BR-20b | 客户端文件内置公钥 | 单文件 HTML 内置 `RK_pub`（以及平台签发公钥 `SSK_pub`）、`joinToken`、房间配置与 `configSig` | 【推断】内置的是**公钥与准入凭证**，不含任何可解密聊天内容的私钥或对称密钥 |
| BR-20c | 每个用户录入昵称进入聊天室时，在本地生成密钥对 | 填昵称时浏览器用 WebCrypto 生成 **UK_i 成员密钥对**，仅本次会话有效 | 【推断】密钥对与昵称绑定，页面关闭即销毁私钥 |
| BR-20d | 公钥发到服务器端，密钥留在本地 | `UK_pub_i` 经 WSS 上传并由服务端广播给全房；`UK_priv_i` 只留本地内存 / IndexedDB，**永不上传** | 服务端登记成员公钥清单，用于按成员封装内容密钥 |
| BR-20e | 服务器加密只保证数据传输安全 | L1 = TLS 1.3（HTTPS / WSS），由服务端终止，**只保护链路，不计入内容机密性** | — |
| BR-20f | 聊天数据都进行两层加密 | L2 = 应用层端到端加密：随机 `K_msg` + AES-256-GCM 加密内容，`K_msg` 再按每个成员的 `UK_pub_i` 做 RSA-OAEP 封装；服务端只见密文与公钥封装，**无解密能力** | 【推断】「两层」定义为 **L1 传输层 TLS + L2 应用层 E2EE**；应用层内部不再叠加第三层，避免把「房间公钥加密」误解为可解密的一层 |
| BR-20g | 保证数据安全 | 服务端全程不持有任何可解密聊天内容的私钥；成员退出后旧密钥无法解密后续消息 | 【推断】逐消息随机 `K_msg` + 会话内成员密钥对 → 天然具备前向保密（见 7.4） |

> **口径结论**：本分支是**真正的端到端加密**（服务端无解密能力），与主线 v5.4.0 的 KDC 模型（服务端生成并持有 `K_room`）**不同**。不得沿用 README 里基于主线模型的模糊措辞，新仓库须独立撰写安全说明。

## 2 产品定位与范围边界

### 2.1 一句话定义

> 一个**以个人为房主、以 HTML 文件为邀请函、以倒计时为寿命、以每成员本地密钥为信任根**的临时端到端加密聊天室：房主在服务器上申请并下载专属客户端，把文件发给朋友，朋友打开后填个昵称就能聊天，服务端从头到尾只见密文，到期后房间和全部数据自动消失。

### 2.2 与主线 v5.4.0 的差异

| 维度 | 主线 v5.4.0 | 私密聊天分支 |
|---|---|---|
| 主体 | 管理员 + 临时/正式身份 | **个人账号**，一人管自己的房间 |
| 身份 | RSA 密钥对 + 挑战应答 + 身份文件（XML） | **无身份体系**，昵称即标识；入房时临时生成成员密钥对 |
| 房间 | 随时创建、长期存在、邀请码加入 | 申请 → 自动通过 → 签发，带 TTL，到期销毁 |
| 入房 | 填地址/端口、导入身份、选房间 | **零输入**（除昵称），地址与凭证全部内置 |
| 客户端 | 一份通用 `chatroom.html` | **一房一份**专属 HTML |
| **加密模型** | **KDC**：服务端生成并持有 `K_room`，技术上可解密 | **双层 E2EE**：TLS + 应用层；内容密钥按成员公钥封装，服务端**无解密能力** |
| 分发 | 服务器 `/download/chatroom.html` 统一下载 | 发起人下载后自行分发，服务端不接触朋友 |
| 数据留存 | 密文归档 + 身份链 + 管理台可查历史 | **到期彻底删除**，不留归档 |
| UI | 登录页、多房间标签、身份库、背景主题、管理台 | 单房间极简界面 |
| 代码 | 主仓 `klmycjs/chatroom` | **独立新仓库**，从主仓复制后独立演进 |

### 2.3 本版包含

个人账号与门户、申请与自动通过、客户端签发、TTL 与人数限制、到期销毁、极简单文件客户端、文字/用户列表/记录导出/语音/视频/文件共享、双层端到端加密、配置与成员公钥的可信验签。

### 2.4 本版不包含【推断】

- 跨房间好友体系、历史消息云端漫游、消息撤回/编辑/@提醒、机器人系统；
- 身份链 / 正式用户 / 邀请码体系（主线概念）；
- 管理台里的机器人池、背景主题、版权管理；
- 移动原生 App、小程序、消息推送；
- 成员退出后的显式 rekey 协议（逐消息随机密钥已覆盖该目标，见 7.4）。

## 3 角色与用例

### 3.1 角色

| 角色 | 说明 | 主要权限 |
|---|---|---|
| **发起人（房主 Owner）** | 拥有个人账号，房间的创建者与唯一管理者 | 登录、申请、下载、分发、查看状态、提前解散、移除成员、导出记录 |
| **参与者（朋友 Guest）** | 拿到 HTML 文件的任何人，无账号 | 填昵称入房、收发消息/文件/语音/视频、导出自己的记录 |
| **管理员 Admin** | 服务器运维者 | 配置配额、审计、强制销毁、吊销凭证；**申请自动通过，无需人工审批** |
| **服务端 Server** | 控制面 + 数据面 | 校验准入、登记成员公钥、转发密文、中继信令、存储密文 blob、定时清理；**不解密任何业务内容** |

### 3.2 用例

| 编号 | 用例 | 主成功流程 | 关键异常 |
|---|---|---|---|
| UC-01 | 注册并登录门户 | 注册 → 登录 → 我的房间 | 口令强度不足、账号已存在、会话过期 |
| UC-02 | 申请建立房间 | 填名称/TTL/人数 → 提交 → **自动通过** → 立即签发 | TTL 越界、人数越界、超出个人配额、名称非法 |
| UC-03 | 审批（自动） | 系统在参数校验通过后直接置为已签发，写一条审计 | 幂等、重复提交不产生第二个房间 |
| UC-04 | 签发并下载客户端 | 生成 RK 密钥对与凭证 → 注入模板 → 下载 | 生成失败、重复下载、签发记录作废 |
| UC-05 | 分发客户端 | 发起人自行发送 HTML 给朋友 | **文件被转发给非预期的人**（固有风险，见 7.3） |
| UC-06 | 朋友昵称入房 | 打开 HTML → 填昵称 → **本地生成 UK 密钥对** → 上传公钥 → 进入房间 | 房间到期/已满、凭证吊销、验签失败、校时失败、证书不受信任 |
| UC-07 | 房间内聊天 | 本地加密 → 按成员公钥封装 → 服务端转发 → 各端本地解密 | 密文校验失败、公钥清单验签失败、断线重连 |
| UC-08 | 打包下载聊天记录 | 客户端本地解密 → 打包 → 下载 | 记录过大、附件缺失、明文泄露提示 |
| UC-09 | 到期自动销毁 | 定时器 + 惰性检查 → 拒绝新连接 → 断开在线 → 删除数据 | 定时器漂移、进程重启后补清理 |
| UC-10 | 提前解散 / 踢人 | 房主操作 → 立即进入销毁 / 移除流程 | 权限校验、并发操作 |

## 4 功能需求

### 4.1 服务端

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| S-01 | 个人账号：注册、登录、登出、会话管理 | P0 | 口令 hash（argon2id/scrypt）、HttpOnly 会话、失败限流 |
| S-02 | 门户页：我的房间列表、申请表单、状态展示、下载入口 | P0 | 独立仓库新建，不复用主线登录页 |
| S-03 | 申请校验：名称、TTL、人数上限 | P0 | TTL 默认 24h、上限 72h；人数受本房上限与服务器全局硬上限双重约束 |
| S-04 | 自动通过 | P0 | 参数校验通过即 `status=issued`，写审计；管理员保留强制介入能力 |
| S-05 | 房间元数据持久化 | P0 | `roomId`、房主、`name`、`expiresAt`、`maxMembers`、状态、凭证哈希、`RK_pub`、签发次数 |
| S-06 | 客户端签发器 | P0 | 生成 **RK 房间身份密钥对**、`joinToken`、`roomId`；组装配置并用平台签发私钥签名；模板注入后一次性下载。**全程不生成、不写入任何可解密聊天内容的对称密钥** |
| S-07 | 准入校验 | P0 | 校验 `joinToken` 哈希、`roomId`、状态、TTL、人数上限；失败统一返回通用错误防枚举 |
| S-08 | **成员公钥登记与可信广播** | P0 | 接收各成员 `UK_pub_i`，维护房间公钥清单；下发时用 `RK_priv` 做 RSA-PSS 签名，客户端用内置 `RK_pub` 验签，**防服务端/中间人偷换公钥** |
| S-09 | WSS 数据面 | P0 | 只转发 `{密文, 每成员一份的密钥封装, 发送方签名}`；心跳、重连、帧大小限制、防重放；**服务端不解密、不尝试解密** |
| S-10 | WebRTC 信令中继 | P1 | 复用主线 `MSG.WEBRTC` 的房间成员校验 + 转发模式，媒体 P2P DTLS-SRTP |
| S-11 | 文件/语音密文通道 | P1 | 加密 blob 存取，按房间与 TTL 归属，到期一并删除 |
| S-12 | 生命周期管理器 | P0 | 定时器 + 惰性检查；到期拒绝连接、断开在线、删除元数据/密文/blob/公钥清单/签发记录 |
| S-13 | 房主操作 | P1 | 提前解散、移除成员、吊销凭证 |
| S-14 | 管理台 | P1 | 房间总览、配额设置、强制销毁、审计日志（**无申请队列**，因自动通过） |
| S-15 | 审计与日志最小化 | P0 | 只记必要事件；**不记消息内容、不记任何私钥、不记昵称明文、不记成员私钥** |
| S-16 | 健康检查与指标 | P2 | 独立 `/pc/api/health`，上报 `pcVersion`、活跃房间数、待清理数 |

### 4.2 客户端（单文件 HTML）

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| C-01 | 内置配置块 | P0 | `serverUrl` / `roomUrl` / `roomId` / `name` / `joinToken` / `roomPubKey`(RK_pub) / `serverPubKey`(SSK_pub) / `issuedAt` / `expiresAt` / `maxMembers` / `configSig` / `clientVersion`。**不含任何私钥或对称房间密钥** |
| C-02 | 启动自检 | P0 | 验签 → 用服务端 `/status` 校正时钟 → 校验 `expiresAt` 与房间状态；失败不发起任何连接 |
| C-03 | 极简入房 | P0 | 首屏**只有昵称输入框 + 进入按钮**；不显示服务器地址、房间 ID、密码 |
| C-04 | **本地成员密钥对** | P0 | 点「进入」时用 WebCrypto 生成 `UK_i`（RSA-2048/3072），`UK_priv_i` 只留本地内存/IndexedDB，`UK_pub_i` 随 `JOIN` 上传 |
| C-05 | 用户列表与公钥状态 | P0 | 在线成员、自己高亮、进入/离开提示、人数/上限显示；可选展示**安全码**供线下比对 |
| C-06 | **两层加密 · 文字消息** | P0 | L1 TLS + L2 应用层：随机 `K_msg` → AES-256-GCM 加密 → 按成员 `UK_pub_i` 逐一 RSA-OAEP 封装 `K_msg` → 发送方 RSA-PSS 签名 |
| C-07 | **本地解密与验签** | P0 | 用自己的 `UK_priv_i` 解开 `K_msg` → GCM 解密 → 用发送方 `UK_pub` 验签 → 渲染 |
| C-08 | 聊天记录打包下载 | P0 | 本地明文导出 JSON + TXT，附件可选；导出前明文风险提示 |
| C-09 | 语音 | P1 | 加密语音条（复用 v5.3 思路）+ 视频通话自带音频 |
| C-10 | 视频 | P1 | mesh WebRTC，媒体 DTLS-SRTP 天然 E2EE，服务端只见信令 |
| C-11 | 文件共享 | P1 | 随机 `K_file` 本地加密 → 密文上传；`K_file` 随一条 `kind=file` 消息按成员封装 |
| C-12 | 到期表现 | P0 | 倒计时、到期后禁用输入、清理本地缓存与 `UK_priv_i` |
| C-13 | 极简 UI | P0 | 单栏：顶栏（房间名 + 倒计时）、消息区、成员列表（可折叠）、输入区、功能按钮；说明文字一律收进 `title` |
| C-14 | 零外部依赖 | P0 | 内联 CSS / 协议常量 / node-forge / 加密核心 / 网络层 / 应用逻辑，单文件 < 500 KB |
| C-15 | 离线可用 | P0 | 双击 `file://` 打开可连服务器；`Origin: null` 需服务端放行 |
| C-16 | 本地数据清理 | P1 | 到期或退出时清除 IndexedDB / localStorage 中的消息、`K_msg` 与 `UK_priv_i` |
| C-17 | **成员公钥清单验签** | P0 | 收到 `MEMBER_KEYS` 时用内置 `RK_pub` 验 RSA-PSS 签名；验签失败拒绝使用该清单并提示「成员身份校验失败」 |

### 4.3 端到端主流程

```text
发起人                      服务端                        朋友
  |-- 登录门户 -------------->|                              |
  |-- 申请(名称/TTL/人数) --->|                              |
  |                          |-- 自动通过 → 生成 RK 密钥对   |
  |                          |   roomId / joinToken          |
  |                          |   注入模板(RK_pub+SSK_pub) + 签名
  |<-- 下载专属 HTML ---------|                              |
  |-- 线下分发 HTML ---------------------------------------->|
  |                          |<-- 填昵称 → 本地生成 UK_i ----|
  |                          |<-- JOIN(joinToken, UK_pub_i) -|
  |                          |-- 登记公钥 → 签名广播名单     |
  |                          |<== WSS：密文 + 按成员封装 K ==>|
  |                          |    服务端只转发，无法解密      |
  |                          |<== WebRTC 信令(媒体 P2P) ====>|
  |                          |-- 到期 → 拒绝/断开/删净        |
```

### 4.4 房间状态机

`待审（瞬时） → 已签发 → 活跃 → 到期或解散 → 已销毁`

- **待审**：因 Q-03 自动通过，该状态仅存在于同一请求的事务内，不留可见队列；
- `已签发`：客户端已生成，尚无人进入；TTL 从**签发时刻**起算（Q-04）；
- `活跃`：至少一人在线，已登记成员公钥清单；
- `到期或解散`：TTL 归零或房主提前解散，立即拒绝新连接并断开在线连接；
- `已销毁`：元数据、密文消息、文件 blob、成员公钥清单、签发记录全部删除，不可恢复。

## 5 非功能需求

| 编号 | 类别 | 可度量指标 |
|---|---|---|
| N-01 | **机密性** | 服务端**不持有任何可解密聊天内容的私钥或对称密钥**；数据库与日志中只有 AES-256-GCM 密文、RSA-OAEP 密文封装与公钥。服务端被攻破（在不主动伪造客户端的前提下）无法还原历史消息 |
| N-02 | 完整性 | 配置块 RSA-PSS 签名 + 成员公钥清单签名 + 消息 GCM 认证标签 + 发送方签名 + 消息序号；篡改或重放被拒绝 |
| N-03 | 生命周期精度 | 到期后 ≤ 60 秒内拒绝新连接；≤ 5 分钟内完成数据删除 |
| N-04 | 单文件体积 | `< 500 KB`，无 `<script src>` / `<link href>`，无网络字体 |
| N-05 | 启动性能 | 现代浏览器打开到可输入昵称 ≤ 2 秒（不含网络）；**UK 密钥对生成 ≤ 500 ms**（RSA-2048 WebCrypto） |
| N-06 | 容量 | 单房间人数默认上限 6，服务器全局硬上限 20；每条消息需做 N 次 RSA-OAEP 封装，N≤20 时单条消息封装耗时 < 50 ms |
| N-07 | 媒体规模 | mesh 连接数 `N(N-1)/2`；N>8 时视频降级或需 TURN/SFU |
| N-08 | 兼容性 | Chrome / Edge / Firefox 最近两个大版本；`file://` 与在线 HTTPS 双通道 |
| N-09 | 可用性 | 服务端重启后从持久化元数据恢复 TTL 与清理计划，不产生「永生房间」 |
| N-10 | 可维护性 | 独立新仓库自带协议常量、构建脚本与回归套件；从主仓复制的代码标注来源与版本，避免两边修复不同步 |
| N-11 | 日志与合规 | 不记录消息明文、任何私钥、昵称明文；审计事件保留期短于房间最大 TTL |
| N-12 | 销毁彻底性 | 服务端删除后成员公钥清单、密文封装、文件 blob 不再存在于任何持久化介质；客户端本地 `UK_priv_i` 同步清理 |
| N-13 | **诚实的安全表述** | 文档与 UI 只写「服务端不具备解密聊天内容的能力」，不写无法证明的绝对化措辞；同时明确告知「拿到 HTML 文件即获得准入资格」与「成员公钥替换」两类边界（见 7.3） |

## 6 约束与假设

### 6.1 技术约束

- 客户端必须是**独立 HTML 单文件**（BR-11）且每房配置不同 → 必须有「模板 + 注入 + 签名」的签发机制。
- 朋友**不输入任何凭据**（BR-10）→ 准入凭证只能内置；**文件本身就是凭证**。
- `UK_priv_i` 永不上传（BR-20d）→ 服务端无法解密，也**无法为晚加入者补发历史消息的密钥封装**（见 7.6 / Q-07 修订）。
- 主线可复用能力：RSA-OAEP/AES-256-GCM + node-forge、单文件构建、WSS `/ws`、WebRTC 信令、密文文件上传、HTTPS 443+80、systemd 部署。因 Q-01 选独立仓库，这些改为**复制后独立演进**（见设计方案第 3 章）。
- 主线 `docs/06-加密协议设计.md` 是 **KDC 模型**（服务端持有 `K_room`），而 `README.md` 宣称「端到端加密」。新分支采用**不同的 E2EE 模型**，须独立撰写安全说明，不得直接复制主线措辞。

### 6.2 运行环境约束（关键风险）

| 约束 | 影响 | 对策（状态） |
|---|---|---|
| **自签 CA 证书** | 原 `flshw.online` 使用自签 CA，朋友的干净浏览器不信任，`https://` / `wss://` 直接失败，与「只填昵称」冲突 | **【已决 Q-12 / P-01 已完成】** 2026-11-16 已用 acme.sh + 阿里云 DNS-01 签发 Let's Encrypt 证书（`flshw.online`、`www.flshw.online`），部署到主线 443 并配置每 6 小时自动续期；已用系统默认信任库验证通过，不再需要自签 CA |
| `file://` 的 Origin 为 `null` | WS 握手与 `/pc/api/*` 需显式放行 | 按房间维度做 Origin 白名单 + `joinToken` 校验，不以 Origin 作为唯一信任依据 |
| 音视频安全上下文 | `file://` 下 `getUserMedia` 策略不一致 | 提供在线 HTTPS 备选入口（Q-13 默认采纳） |
| 混合内容 / CORS | `file://` 页面访问 HTTPS API 需 CORS | `/pc/api/*` 统一 CORS 头，上传/下载端点一并处理 |
| 本机时钟不准 | 客户端按 `expiresAt` 判断会误判（主线曾因本机快 9.5 分钟踩 `timestamp skew`） | 以服务端 `/status` 的 `serverTime` 校正，客户端只做展示 |
| **独立仓库 / 共用域名与 443** | 用户第三轮确定两个项目都发布在 `flshw.online`，分别挂在虚拟目录 `chat` 与 `Pchat` | **【Q-16 已收敛】** 沿用主线已在 443 的 TLS 与 systemd unit；根路径做双项目导航，`/chat/` 提供原客户端，`/Pchat/` 先占位、上线后替换为新服务入口。新项目 API/WSS 必须使用独立前缀（建议 `/pc/api/*`、`/pc/ws`）避免与主线冲突；`pc.flshw.online:8443` 方案作废 |

### 6.3 假设【推断】

- 朋友使用现代桌面浏览器，能打开 HTML 并访问互联网；
- 发起人能通过某种渠道把文件发到朋友手上；
- 服务端有公网可达的 HTTPS 域名与可信证书（M5 前完成）；
- 生命期内服务端持续运行，或重启后能恢复 TTL 状态；
- 不需要消息云端长期漫游、不需要跨设备同步；
- 成员私钥保存在浏览器本地，页面关闭或到期即失效，不做跨设备恢复。

## 7 安全与威胁模型

### 7.1 资产与信任边界

- **资产**：聊天明文、语音/视频媒体、共享文件、各成员 `UK_priv_i`、逐消息 `K_msg`、`joinToken`、成员昵称与在线关系。
- **可信方**：发起人浏览器、朋友浏览器（各自只信任自己的私钥）。
- **不可信方**：网络旁路者、CDN/代理、磁盘/备份泄露者、拿到 HTML 副本的第三方；**服务端在内容机密性上视为不可信**（只见密文）。
- **边界**：服务端只接收与转发密文；**HTML 文件本身位于准入信任边界内**——谁持有文件，谁就能进入房间。

### 7.2 加密模型：**D 档 · 双层加密 + 每成员密钥对**（Q-02 已决）

v0.1 给出的 A / B / C 三档均基于「一个共享 `roomKey`」，已被用户第二轮细化取代。最终模型如下：

| 层 | 名称 | 算法 | 密钥来源 | 谁能解密 | 服务端可见 |
|---|---|---|---|---|---|
| **L1** | 传输层 | TLS 1.3（HTTPS / WSS） | 服务端证书 | 服务端终止 TLS | 应用层密文 |
| **L2** | 应用层内容加密 | AES-256-GCM | 每消息随机 `K_msg` | 持有 `K_msg` 的成员 | 密文 `ct/tag/iv` |
| **L2-key** | 应用层密钥封装 | RSA-OAEP-SHA256 | 按每个成员 `UK_pub_i` 分别封装 `K_msg` | 持对应 `UK_priv_i` 的成员 | 每成员一份密文封装（无法解开） |
| 身份 | 消息签名 | RSA-PSS-SHA256 | 发送方 `UK_priv_i` | 任何人可用 `UK_pub` 验签 | 签名（可验不可伪造） |
| 身份 | 名单/配置签名 | RSA-PSS-SHA256 | `RK_priv` / `SSK_priv` | 客户端用内置公钥验签 | 签名 |

**关键结论**：服务端从建立房间到房间销毁，**全程不持有任何可解密聊天内容的私钥或对称密钥**。这比 v0.1 推荐的 B 档（签发瞬间见过 `roomKey`）更强，可以准确表述为端到端加密。

**房间公钥 `RK_pub` 的确切用途（对 BR-20a 的必要补全）**：
1. 验证服务端下发的**成员公钥清单**签名，防止偷换公钥（见 T-11）；
2. 验证房间公告与配置中的房间身份字段；
3. **不用于加密聊天内容**——朋友只持有公钥，若用它加密内容将无人可解。

> **设计取舍说明**：`RK_priv` 默认由服务端签发器持有（贴合「聊天室建立时生成密钥对」的字面语义）。它只是**签名私钥**，不是解密私钥，因此不破坏「服务端不能读聊天内容」。代价是理论上服务端可伪造名单签名，需以 T-11 的缓解措施覆盖；若要求完全消除该风险，可升级为「`RK_priv` 由房主浏览器本地生成并保管」（Q-15，列为增强项）。

### 7.3 威胁清单

| 编号 | 威胁 | 缓解措施 | 状态 |
|---|---|---|---|
| T-01 | **HTML 文件泄露 / 被二次转发**：拿到文件的人获得准入资格 | 短 TTL、人数上限、房主可提前解散/踢人、到期销毁、成员列表可见；**文件即凭证是固有风险，必须在下载页与 UI 上告知**。注意：新模型下转发者**仍然无法解密他人消息**（没有别人的 `UK_priv`），风险较 v0.1 显著降低 | 部分缓解 |
| T-02 | 房间 ID / 凭证被枚举或猜测 | `roomId` 与 `joinToken` 均 128 bit 以上 CSPRNG；失败统一返回通用错误；按 IP 限流 | 已覆盖 |
| T-03 | 配置块被篡改（改 TTL / 人数 / 地址 / `RK_pub`） | 服务端私钥对 canonical 配置签名（`configSig`），客户端用内置 `SSK_pub` 验签；**`RK_pub` 必须纳入被签名字段**，否则可被替换成攻击者的公钥 | 已覆盖 |
| T-04 | 重放攻击 | 消息序号 + 服务端校正时间戳 + 一次性 nonce；沿用主线 `ERR.REPLAY` 思路 | 已覆盖 |
| T-05 | 中间人替换服务器公钥 | 公网可信证书（Q-12）+ 配置签名；不用 TOFU 指纹核对（朋友是小白用户） | P-01 已完成 |
| T-06 | 昵称冒充 | 房主标识由签发关系确定；昵称仅展示，同名加后缀区分；消息签名绑定发送方 `UK_pub`，昵称本身不可伪造他人消息 | 已覆盖 |
| T-07 | 文件上传滥用 / DoS | 类型白名单、体积上限、单房配额、频率限制、到期一并清理 | 已覆盖 |
| T-08 | 到期后数据残留 | 定时器 + 惰性双检查、级联删除密文/封装/文件/公钥清单、清理临时文件与日志 | 已覆盖 |
| T-09 | 明文导出泄露 | 导出前明确提示「导出文件为明文」；可选加密导出 | 已覆盖 |
| T-10 | 客户端本地缓存残留 | 到期/退出清 IndexedDB 与 localStorage 中的 `UK_priv_i` 与消息；**朋友本地副本不可由服务端删除**，需 UI 告知 | 已覆盖 |
| **T-11** | **成员公钥替换攻击**：恶意/被攻陷服务端把自己生成的公钥冒充某成员，让发送方用假公钥封装 `K_msg`，从而解密消息 | ① 成员公钥清单必须由 `RK_priv` 签名、客户端用内置 `RK_pub` 验签；② 每个成员 `UK_pub` 附自签名（用自己 `UK_priv` 签），客户端交叉校验；③ 可选展示**安全码**（全体公钥指纹的短哈希）供线下比对；④ 终极方案是 Q-15：把 `RK_priv` 移到房主本地 | **新模型最关键的新增风险，M2/M3 必须实现 ①②** |
| **T-12** | **房间签名私钥 `RK_priv` 泄露**：攻击者可伪造任意成员名单 | `RK_priv` 只存服务端密钥库、不写日志/备份；每房一对、房间销毁即删除；优先采用 Q-15 的房主本地保管 | 开放（Q-15） |
| T-13 | 独立仓库复制代码后，主线安全修复未同步 | 复制清单标注来源 commit；建立「主线加密相关改动 → 检查新仓是否需要同步」的评审项 | 新增（对应 R-11） |

### 7.4 前向保密（Q-08 修订后关闭）

v0.1 曾建议「本版不做成员退出 rekey」。**新模型天然具备更强的逐消息前向保密**，因此该项关闭：

- 每条消息使用**独立随机 `K_msg`**，不复用、不派生自长期房间密钥；
- `UK_i` 只在本次会话内有效，页面关闭即销毁 `UK_priv_i`；
- 消息只把 `K_msg` 封装给**当时在线且已登记公钥**的成员；成员退出后，服务端不再为其生成封装 → 即使该成员保留了 HTML 与旧消息密文，也无法解开退出后的新消息；
- 无需额外 rekey 协议，安全模型仍为「**文件即凭证，TTL 即边界**」。

> 代价：`UK_priv_i` 一旦因页面刷新丢失，该成员**无法再解密自己历史收到的消息**（历史封装是给旧公钥的）。因此客户端需在会话内把 `UK_priv_i` 存在 IndexedDB，并在到期/退出时清除；刷新页面应复用同一密钥对而非重新生成。

### 7.5 「两层加密」的准确表述

| 说法 | 是否正确 |
|---|---|
| 「聊天数据经过两层加密：TLS 传输层 + 应用层端到端加密」 | ✅ 正确，文档与 UI 采用此表述 |
| 「服务端加密只保证传输安全」 | ✅ 正确，对应 L1；L2 的密钥完全在各成员浏览器本地 |
| 「用房间公钥再加密一层」 | ❌ 不成立：房间公钥用于验签，若用于加密内容则朋友端无对应私钥可解 |
| 「服务端绝对无法看到任何信息」 | ❌ 过度承诺：服务端仍能看到房间 ID、成员公钥、昵称（若未加密）、消息时序、文件大小与在线关系，且理论上可尝试 T-11 攻击 |

### 7.6 晚加入者历史（Q-07 技术性修订）

新模型下，历史消息的 `K_msg` 只封装给**当时已登记公钥**的成员。新成员后来生成的 `UK_pub` 不在历史封装列表中，因此：

- **默认冻结为：晚加入者不拉取 / 无法解密历史消息**；
- 服务端仍可暂存密文供同期成员断线重连补拉，**到期即删**（Q-10 不变）；
- 若业务上必须让晚加入者看历史，需要「由在线成员用新成员公钥重新封装历史 `K_msg` 后补发」，会显著增加复杂度，**本版不做**，列为后续增强项。

## 9 验收标准

| 编号 | 可测试验收项 |
|---|---|
| AC-01 | 注册登录后能提交含名称/TTL/人数的申请；TTL > 72h 与人数越界被拒绝并给出提示 |
| AC-02 | 提交后**无需管理员操作**即自动通过并生成专属 HTML；两份不同房间的 HTML 配置块不相同 |
| AC-03 | 朋友双击 HTML，首屏只出现昵称输入框；填昵称后无需任何其它输入即可进入房间 |
| AC-04 | 修改 HTML 中任一内置配置字段（含 `RK_pub` / `SSK_pub`）后，客户端验签失败并拒绝连接 |
| AC-05 | 抓包 / 查库：消息、文件、语音均为 AES-GCM 密文 + 按成员 RSA-OAEP 封装；**服务端数据库与日志中不存在任何可解密聊天内容的私钥或对称密钥** |
| AC-06 | 人数达到上限后第 N+1 个客户端被拒绝并提示房间已满 |
| AC-07 | TTL 到期后：新连接被拒、在线断开、元数据/密文/公钥清单/文件全部删除、重启后不复活 |
| AC-08 | 客户端能导出聊天记录，导出内容可读；导出前有明文风险提示 |
| AC-09 | 用户列表实时反映成员进入/离开；文字、语音、视频、文件在 2 人以上房间可用 |
| AC-10 | 单文件 < 500 KB、无外部资源引用、Chrome/Edge/Firefox 均可打开 |
| AC-11 | **干净浏览器（未导入任何 CA）**能连上 WSS（验证 P-01 证书） |
| AC-12 | 服务端日志中不出现 `joinToken` 明文、任何私钥与消息明文 |
| **AC-13** | 两个成员各自生成的 `UK_pub` 不同；服务端能查到两份公钥且**查不到任何 `UK_priv`**；两方可互相解密对方消息 |
| **AC-14** | 篡改成员公钥清单（替换为攻击者公钥）或去掉签名后，所有客户端拒绝使用该清单并提示「成员身份校验失败」 |
| **AC-15** | 成员 A 退出后，用其旧公钥无法解开退出后新消息的 `K_msg` 封装（前向保密） |
| **AC-16** | 断线刷新页面后复用同一 `UK_i`，仍能解密自己历史收到的消息；到期后本地 `UK_priv` 被清除 |
